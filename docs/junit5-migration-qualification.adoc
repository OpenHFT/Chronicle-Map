== Timeout and failure semantics

A JUnit 4 `@Test(timeout=...)` runs its method on another thread from the fixture methods.
Jupiter's default `@Timeout` uses the same thread unless configuration overrides the thread mode.
An external qualification probe exercised both forms and the actual migrated `JSR166TestCase`
fixture: setup and teardown ran, the Jupiter method shared their thread, and an assertion from a
worker failed its owning Jupiter invocation with the original throwable. This qualifies that
fixture and configuration; it is not a claim that the annotations have identical semantics.

`TrickyContextCasesTest` now completes setup before asserting the specific nested removal or
worker write failure. The worker must finish with an `ExecutionException` whose cause is exactly
`InterProcessDeadLockException`. A `Future.get` timeout or an unrelated setup/worker exception
cannot satisfy that assertion. Context release precedes bounded worker termination, and map close
follows termination; cleanup failures are suppressed on an existing assertion failure.

Relocation currently publishes a new entry before acquiring its write lock. Qualification observed
that a lock-timeout rejection can therefore follow publication of the new value. This migration
does not add a transactional rollback guarantee or change that production ordering. Any such
contract change needs its own accepted runtime correction and regression.

Fresh platform CI, strict temporary-directory cleanup and the restored memory-release assertions
remain acceptance requirements. A queued build is not a passing result.
